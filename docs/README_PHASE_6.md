# Phase 6 - Build and Test Execution

## Goal

Add controlled ROS 2 project build and test execution without breaking the existing modular architecture or filesystem security boundary.

Phase 6 introduces controlled process execution for:

```text
build_project
run_tests
```

The implementation uses `colcon build` and `colcon test`.


The MCP and application layers do not directly use `subprocess`.

## ExecutionAdapter

The abstract execution interface defines controlled process execution independently from the concrete subprocess implementation.

The interface accepts:

```text
command
working_directory
timeout_sec
```

and returns an `ExecutionResult`.

## ExecutionResult

Execution results contain:

```text
command
working_directory
return_code
stdout
stderr
timed_out
```

The result object is immutable.

## Command Policy

Phase 6 introduces an explicit command allowlist.

Currently allowed:

```text
colcon build
colcon test
```

Optional package selection is supported:

```text
colcon build --packages-select <package...>
colcon test --packages-select <package...>
```

Other commands and unsupported colcon options are rejected.

Examples that are rejected include:

```text
rm -rf /
colcon list
colcon build --base-paths /tmp
colcon build --build-base /tmp/build
colcon build --install-base /tmp/install
colcon test --test-result-base /tmp/results
```

Package names are validated before command execution.

## SubprocessExecutionAdapter

The concrete execution adapter uses Python `subprocess.run`.

The process is executed with:

```text
shell=False
capture_output=True
text=True
check=False
timeout=<configured value>
cwd=<validated workspace>
```

No shell interpretation is enabled.

## Working Directory Security

Before execution, the requested workspace path is validated through `SafeFilesystem`.

The execution working directory must stay inside the configured project root:

```text
/home/sarvg/projects/robotics/ros2_mcp
```

Attempts to escape this root are rejected.

## Timeout Configuration

Execution timeouts are configured externally.

Current configuration:

```toml
[execution]
build_timeout_sec = 120.0
test_timeout_sec = 120.0
```

The configuration is stored in:

```text
config/ros2_mcp.toml
```

The values are loaded through:

```text
src/ros2_mcp/config/settings.py
```

## Generated Package Test Configuration

Generated ROS 2 Python packages contain a local:

```text
pytest.ini
```

with:

```ini
[pytest]
testpaths = test
```

This isolates generated package tests from parent project pytest configuration.

Generated package metadata also includes:

```xml
<test_depend>python3-pytest</test_depend>
```

## Architecture Decisions

Phase 6 establishes these rules:

* Process execution is isolated behind an ExecutionAdapter.
* MCP never directly executes processes.
* Application services never directly use subprocess.
* Only explicit colcon commands are allowed.
* Unsupported colcon path options are rejected.
* Working directories must stay inside the configured root.
* Shell execution is disabled.
* Execution timeouts are configurable.
* stdout and stderr are returned to callers.
* Build and test exit codes are preserved.
* Generated ROS packages isolate their pytest configuration.
* Real E2E build and test workflows are part of the test suite.

## Known Limitations

Phase 6 currently supports only:

```text
colcon build
colcon test
```

It does not yet support:

```text
colcon test-result
ros2 run
ros2 launch
arbitrary shell commands
environment modification
parallel execution policies
resource limits
process cancellation
streaming process output
```

These can be evaluated later without changing the core architecture.

## Real ROS 2 Runtime Verification

Phase 6 was verified with a real ROS 2 Jazzy runtime, not only with unit and integration tests.

The MCP server successfully performed the following workflow:

1. Created a ROS 2 workspace.
2. Created an `ament_python` package.
3. Created a Python ROS 2 node.
4. Created a launch file.
5. Created a parameter YAML file.
6. Created package tests.
7. Built the package with `colcon build`.
8. Tested the package with `colcon test`.
9. Installed the generated node as a ROS 2 executable.
10. Started the generated node with `ros2 run`.
11. Verified the running node through the ROS graph.

The generated executable was detected with:

    ros2 pkg executables demo_robot

Result:

    demo_robot demo_node

The generated node was started with:

    ros2 run demo_robot demo_node

The ROS graph reported:

    /demo_node

`ros2 node info /demo_node` also confirmed the expected ROS 2 parameter services and standard publishers.

This verifies the complete path:

    MCP project generation
        -> ROS 2 package
        -> ROS 2 node
        -> colcon build
        -> installation
        -> ros2 run
        -> ROS graph

The persistent demo used for this verification can be recreated with:

    python scripts/create_demo_project.py
